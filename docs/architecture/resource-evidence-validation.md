# Resource fleet evidence validation

This leaf checks W1 evidence consistency and selected duration/plateau conditions when a soak is claimed. It does not run workloads or certify W0–W10, authenticate the collector, prove that supplied timestamps are truthful, or convert synthetic fixtures into live acceptance.

Run from the candidate checkout with Node 24:

```sh
rtk proxy node --import tsx scripts/verify-resource-evidence.ts /private/evidence/manifest.json /private/evidence/expected-candidate.json
```

The expected candidate is supplied independently of the manifest. It is a strict object with `sourceSha` (40 hex), `dirty` (boolean), `profileSha256`, `configSha256` (64 hex each), and `imageDigest` (`sha256:` plus 64 hex). Every run and optional soak must match it exactly. Comparing a manifest to an expected identity copied from that same manifest supplies no independent candidate assurance.

`evals/assertions/resource-fleet-schema.ts` exports the exact `ResourceFleetEvidenceSchema` v1 and inferred type. `tests/evals/resource-fleet-fixture.ts` is a complete **synthetic** construction example, not a live evidence artifact. The manifest contains:

- Candidate identity, host hardware/OS/Node/pnpm versions, explicit measurement boundaries and bounded sampling policy.
- One or more warm-up runs followed by at least three distinct, nonoverlapping measured runs. Every attempted run, including failures, belongs in the manifest; the validator cannot discover omitted attempts. Both Claude and Codex must appear in measured runs.
- Exactly eight workers per run with unique worker/runtime/immutable container identity, generation, subscription authentication, CLI version, model/effort and exact image. Each has readiness and runnable intervals, at least two ordered provider-native progress events, and an outcome with evidence references. A common barrier must lie inside every runnable interval. All eight post-barrier progress windows must intersect; sequential progress cannot pass merely by declaring long runnable intervals. This establishes consistency of runnable-provider overlap, not simultaneous CPU-intensive execution or cloud-wait utilization.
- Timestamped samples from start through finish. Host physical usage includes sampler cost and excludes the VM; attributable VM physical usage includes guests. Guest cgroup usage, reservations and configured maxima remain separate. Observed total is host plus attributed VM; cgroups are never added again. Every sample over 8 GiB, and every reservation-plus-fixed/uncertain/control-margin total over 8 GiB, is retained as an individual breach. Configured maxima are diagnostic, not usage.
- Read-only RPC p95 under 250 ms, event-loop p99 under 100 ms, complete capture, zero unexplained cleanup resources, and reconciled terminal/evaluation counts. Missing metrics, unknown attribution, missing coverage or excessive sample gaps are unverified. The declared sample interval is 100–15000 ms; maximum gap is at most twice that interval and never above 30000 ms.
- Optional `soak` with actual timestamp duration at least 24 hours, continuous samples, a warmed baseline and at least 100 unique chronological spawn/settle/park/wake/retire/observed cycles in the same settled phase. Every measured plateau point must stay within max(10% of baseline, 64 MiB). Positive late-window fitted memory/process/disk trends remain unverified pending independent noise/retention assessment; no silent tolerance is invented. These checks alone do not establish W8 fairness, mixed-load coverage, pressure behavior, or all acceptance gates.

Artifacts use basenames only (no directory traversal) and one of four sanitized kinds. `resourceEvidenceArtifactBodies(manifest)` returns the exact versioned JSON bodies to write, keyed by artifact ID: barrier/readiness/native progress, resource rows, worker outcomes, or soak lifecycle records. Write those bodies, then set each manifest artifact's exact UTF-8 byte length and SHA-256. The helper does not authenticate records; collectors must derive them from independently captured native/runtime facts. Hashes bind files to declared content and detect later changes.

CLI verification checks artifact hashes, sizes and exact sanitized-record equality with the manifest. Extra transcript/command/environment fields fail equality. Do not include private raw logs in this directory or manifest: retain them separately under a bounded private retention policy. Files must be regular, cannot be final symlinks, and are read through capped buffers with post-read change checks. Manifest limit is 32 MiB, expected identity 4 KiB, each artifact 8 MiB, total declared artifacts 128 MiB, at most 64 artifacts and 100,000 aggregate resource samples. Parent directories resolve to a canonical artifact root; only declared basenames are opened within it. This prevents path traversal, not a malicious collector fabricating a self-consistent package.

The CLI emits one JSON report. Status is `failed`, `unverified`, or `evidence-consistent`; only the last exits zero, and it always includes the limitation that consistency and hashes do not authenticate collection or prove live acceptance. Pure `assessResourceFleetEvidence()` reports `structurally-consistent` until file verification occurs. Do not label either status “MacBook verified” or “W1 passed” without the independent live collection/review gate.
