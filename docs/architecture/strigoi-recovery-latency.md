# Bounded conversational recovery

The combined PR168/169 live fixture recovered the correct publication constraint, but its adoption took 178.717 seconds and its ordinary answer arrived about 188.5 seconds after acceptance. The packet held 124 source parts / 157,215 source-text bytes: 55 instruction revisions, 56 lifecycle events, configuration copies, session records and a small conversation. This observation motivates reducing model-facing recovery work; it does not prove that every second was caused by evidence volume.

## Recovery contract

Original immutable evidence, coverage identifiers and packet hashes are unchanged. A model-facing view selects conversational originals, the latest observed revision of each distinct instruction envelope, session launch context, and work/attention/workflow evidence. Broker lifecycle metadata and recognized internal recovery exchanges remain in the full archive. Session records and native system/developer frames stay visible because task instructions may exist nowhere else after an abrupt failure; role alone does not establish regenerable configuration. Different message contents or addressing are never collapsed. Unrecognized evidence stays visible. Unknown submission/delivery outcomes remain present in the latest instruction record and remain fenced by the existing delivery protocol. Observation order, not wall-clock timestamp, selects revisions.

Views up to 256 KiB are embedded in the adoption prompt to avoid serial model/tool round trips. Larger views use linked pages with the existing 64-reference/32-KiB-source-text limits. There is no total-evidence truncation to satisfy a performance budget. The full archive path remains available for deliberate retrieval. Per-adoption accounting artifacts record source categories, bytes, selected/deferred counts, view size and preparation time; these are measurements, not token estimates or control authority. This bound is a transport optimization, not a claim that arbitrarily large first-recovery histories meet the latency target.

Adoption may include `recovery: {version: 1, baseMutationId?: string}`. Its account must preserve prior checkpoint commitments, restrictions, unresolved decisions and uncertain outcomes, updated by inspected changes. A base names an earlier durable protocol-marked adoption receipt; missing, cyclic or forward chains are rejected. Legacy accounts are not assumed to satisfy this contract. The next recovery uses that account and new source revisions. If the base's covered sources are unavailable in the packet, the view falls back to originals instead of silently treating them as covered.

`handledSourceIds` still names only original source parts actually inspected in that adoption turn. Reading a derived checkpoint does not claim its originals were reread. Deferred originals are not acknowledged and remain in `pending()`. Conversational adoption is distinct from exhaustive historical coverage; current instructions govern and historical evidence never grants new authority. The checkpoint remains a model account, with semantic correctness requiring live qualification.

Native adoption replies use compact `handledSourceIndices` instead of copying 64-character hashes. The observation adapter expands them only against the source map in the broker's durable original instruction. Duplicate/out-of-range indices, missing/ambiguous maps and model-supplied mappings are rejected. Expanded receipts still pass the unchanged identity, packet and original-coverage checks; stored receipts and public acknowledgments retain full source IDs. Legacy native receipts remain readable.

This is an additive receipt field within the existing state schema. Older readers may discard the optimization marker and fall back to full evidence; deployment rollback still requires compatibility qualification. No instruction submission fence, retirement identity, notification consumption rule or journal format is replaced.

## Acceptance

Proposed targets are 15 seconds for an ordinary settled answer and 30 seconds for a recovery answer, measured from message acceptance through canonical completion and idle. Startup readiness is measured separately. Provider time, view preparation, archive bytes and selected bytes must be reported separately. An early projection reached 5,497 bytes / 8 parts, but independent review required preserving session launch context and the latest packet checkpoint; that early number does not describe the final candidate. Final measurements belong to the exact candidate's qualification report.

Qualification must cover repeated restart before adoption, provider loss after adoption, restart with adopted obligations, conflicting user corrections, unresolved decisions, uncertain effects, long histories, invalid checkpoint ancestry and unread-coverage preservation. Model/tool latency is variable: retain every bounded failure and report the distribution rather than choosing the fastest sample. Keep shared rollout and legacy reconciliation held until the final candidate is qualified.

## Native readiness after terminal-only work

Codex 0.169 can emit another OSC7501 working/done interval after a canonical answer, including during terminal-title updates, without recording another native task lifecycle. The busy fence correctly rejects the old task completion, but that previously left a queued follow-up permanently at `native-evidence-unavailable`.

For a marked, exactly bound host Codex session whose screen is ready but native activity remains uncertain, the broker now performs a bounded metadata-only `thread/read` against the existing managed daemon. It requires the exact native thread ID, working directory, same canonical transcript file, runtime idle, and permission to accept direct input. It then rereads the native transcript and binding; changed native evidence or identity is refused. Input, generation, activity-revision, modal, active-work and source-error fences remain intact. The native completion must still postdate actual input and the runtime generation. A readiness observation supplies no canonical completion, instruction receipt or retirement proof. Container sessions never use a host-daemon readiness read.

The read has a one-second total deadline and never starts/resumes a thread or daemon. Failed or unavailable reads retain the existing delivery hold. Managed daemon session symlinks are resolved to the same canonical file, not accepted by basename or approximate matching.

Validation on 2026-11-16 includes replay of the exact retained failing terminal suffix into a private live production-component controller. The real native daemon confirmed idle, the bound transcript stayed unchanged, and the original queued correction completed in 8.735 seconds. Private evidence is retained under `/private/tmp/cds-01sakU`. The first candidate's literal path comparison rejected the managed-home symlink spelling; the canonical-file comparison fixes that refusal and has a regression test. Source and runtime tests cover refusal on changed identity, native activity, source boundaries, actual input, generation, revision, current busy cycles, timeout and read errors.

One additional full recovery run completed restart adoption/follow-up in 17.108 seconds and provider-loss recovery in 29.894 seconds, but the forced-crash follow-up missed the proposed 30-second end-to-end budget. Its eventual adoption completion is not a passing bounded answer. These individual observations do not establish a percentile guarantee. The original 180-second gate and the stronger 30-second target must remain distinguishable in qualification reports.

Legacy resident reconciliation is still an operational prerequisite for activation. Its held successor lacks a process-group marker, native binding and turn ledger. Runtime idle is not retirement; this readiness repair deliberately supplies no way to clear that hold or fabricate ownership evidence.


A second worker-side MCP run isolated a closing-frame race: the `done` marker for the existing work interval can precede erasure of its old Working footer in the same terminal update. Treat that exact active-to-inactive interval edge as a redraw of known work. It does not create native completion evidence, does not exempt a new interval, and does not exempt a later independent working frame. Regression cases require an already valid native end and preserve later-work fences. The earlier worker fixture at `/tmp/cdmcp-VVyx65` is retained as a failed gate; it must not be counted as passing because the initial canonical answer alone completed.
