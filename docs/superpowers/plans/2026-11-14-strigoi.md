# Strigoi Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The operator's opt-in skill policy takes precedence; do not start either workflow until the execution method is selected.

**Goal:** Build Strigoi, a durable resident Fleet Orc that starts quietly with the broker and preserves useful understanding and unfinished work across succession and failure.

**Architecture:** Add a dedicated resident binding to the existing orchestrator authority model. Use serialized succession, one durable activation commit, and existing instruction, worker, attention and transcript services for continuity. Separate mechanical guarantees about Cyberdeck operations from evaluation of the successor's judgment and external-tool behavior.

**Tech Stack:** Existing TypeScript, Zod, Vitest, private fsynced persistence, broker/provider adapters; Node `>=24.18.0 <25`, pnpm `11.5.0`. No new dependencies. Codex is the first provider to qualify.

**Spec:** [Approved design](../specs/2026-11-14-strigoi-design.md), [ADR 0001](../../adr/0001-strigoi-durable-fleet-orc.md), [product brief](../../design/strigoi-brief.md).

**Status:** Tasks 1–9 independently reviewed complete; Task 10 source/fixture acceptance and controller full check/test/build passed. Task 10/whole-branch review and live qualification remain pending. [Evidence](../../setup/strigoi-acceptance.md).

## Global Constraints

- Display/code name: Strigoi. Alfred is a conversational alias for the same resident.
- One configured resident exists per broker state directory, under the existing broker singleton ownership.
- When no work is pending, startup and idle residence make zero model inference calls.
- No second freely acting incarnation is prepared alongside the incumbent.
- Existing peer-create approval and directed-worker-handoff policies continue to apply.
- Routine conversation, inputs arriving during cutover, owned-worker results, queued instructions and attention waits must automatically continue after planned renewal; a hold is a failure in these cases.
- No automatic provider fallback. Exact live model/effort/cwd are selected at enablement.
- The admission barrier covers Cyberdeck-controlled operations, not every provider-native or connected tool.
- No compulsory monitoring assignment, charter, Ammo integration, provider budgeting, subordinate recovery engine, or new hierarchy.
- Preserve existing primary/peer identities, dirty work, running sessions and evidence. Documentation approval does not authorize live enablement, publication, or restarting the operator's broker.
- Commands below use RTK. All source changes and their tests belong in an isolated execution checkout; this planning turn edits documents only.

## Review Focus

1. Suspension arrives during launch/commit/acknowledgement: it must win and remain effective after restart (Tasks 2, 4, 6, 10).
2. A delayed predecessor call or liveness callback arrives after cutover: it must not mutate state or orphan successor ownership (Tasks 3, 7).
3. An old but still referenced native transcript reaches normal retention age: preserve it before cleanup; a damaged pin index must not silently erase it (Task 5).
4. An instruction was rendered but its submission outcome is unknown: never classify it as safe to retype (Tasks 6, 8, 10).
5. Grant revocation or a worker transfer races with renewal: the new incarnation must not restore obsolete authority from its packet (Tasks 3, 7, 8).

## Concrete implementation choices

The following settle details delegated to planning; they do not enlarge the approved scope.

- Binding kind `resident`, key `resident:strigoi`, scope `{kind: "fleet"}`. Derive
  controller/family through `orchestratorController()`; Strigoi's family is its own.
  Its binding adds `resident: {name: "strigoi", incarnation: number}`; the session
  record remains a regular Orc. Ordinary primary/peer keys and scope semantics remain unchanged.
- Persist resident state and its active binding together in
  `<state>/orchestration/strigoi/records.jsonl`. This is a separately validated shard
  of `OrchestratorStore`, not a second controller directory. Existing readers still
  consult that store. A resident-only corruption must disable Strigoi without making
  unrelated binding reads fail. No duplicate active binding in `bindings.jsonl`.
- Each append has a revision, mutation ID, request hash and complete next state.
  `compareAndSwap` serializes read/check/append/fsync, supports durable replay of the
  same request, and rejects a reused ID with different content. The active binding
  and incarnation advance in that one record. Never append after an ignored partial
  tail: preserve the evidence and repair the journal boundary through the existing
  private-file/atomic-write primitives before further writes.
- A narrow internal launch option supplies a preallocated session ID and persists
  the provisional session before spawn. Do not expose caller-chosen IDs on public
  `session.start`. A retry reconciles the recorded attempt; it cannot blindly launch
  a second process under either a new or the same ID.
- Start with manual/agent-requested renewal plus failure recovery. Report context
  headroom as unknown until an adapter proves a usable metric; no guessed automatic
  threshold or transcript-byte heuristic in the first release.
- Limits: 32 KiB UTF-8 model-written checkpoint prose, 256 KiB packet manifest,
  64 source references/page, 32 KiB returned source text/page. These bound transport,
  not total obligations: paginate mechanical inventories, never truncate them silently.
- Retry unexpected launch failures after 1, 5 and 30 seconds, at most three attempts
  per recovery episode. Persist attempts and due times. Authentication/configuration
  failures hold immediately. Explicit resume starts a new bounded episode. Timers
  do not invoke inference. Adopt/checkpoint turns get at most two attempts each per
  transition; 120 seconds per attempt before a visible hold, with no automatic
  concurrent retry while execution termination remains unresolved.
- Safe-boundary wait is 120 seconds before a visible `awaiting-safe-boundary` hold;
  do not interrupt an active task just to meet the timer. A later actual boundary
  can continue the same transition unless suspended or explicitly aborted.
- Retain all Strigoi incarnation transcripts and referenced source records initially.
  No automatic release policy in v1; inspect reports counts/bytes. This deliberately
  favors recovery evidence over a new semantic garbage collector.

### Shared contracts

Task 1 defines these domain types; reuse them rather than creating per-layer shapes:

```ts
type StrigoiIdentity = { sessionId: string; incarnation: number; generation: number };
type StrigoiSelection = { provider: "codex"; model: string; effort?: ReasoningEffort; cwd: string };
type StrigoiDesired = "enabled" | "suspended" | "disabled";
type StrigoiPhase = "requested" | "checkpointing" | "sealed" | "retiring"
  | "launching" | "committed" | "adopting" | "reconciling" | "complete" | "aborted";
type StrigoiSourceRef = {
  kind: "turn" | "instruction" | "worker-event" | "attention" | "workflow" | "artifact";
  id: string; revision: string; sha256?: string;
};
type StrigoiPacketRef = { artifactId: string; sha256: string; coverageId: string };
type StrigoiHold = { code: string; detail: string; sourceIds: string[] };
type StrigoiTransition = {
  id: string; expectedIncarnation: number; reason: string; phase: StrigoiPhase;
  predecessor?: StrigoiIdentity; successor?: StrigoiIdentity; packet?: StrigoiPacketRef;
  attempts: number; nextAttemptAt?: string;
};
type StrigoiState = {
  schemaVersion: 1; revision: number; desired: StrigoiDesired;
  selection?: StrigoiSelection; activeBinding?: OrchestratorBinding;
  incarnation: number; transition?: StrigoiTransition;
  latestPacket?: StrigoiPacketRef; retainedSessionIds: string[];
  hold?: StrigoiHold; updatedAt: string;
};
```

Zod validation refines resident-only binding key/scope, identity consistency, positive
generation, increasing incarnation, selection required when enabled, and valid packet
hashes. `StrigoiInspection` combines that durable state with the existing runtime truth,
readiness/adoption receipt, and usage (unknown allowed); derived status is never authority.
`StrigoiPacket` contains version, author identity, timestamp, prose, exact coverage and
paged source inventory references. `StrigoiAdoption` contains identity, packet hash,
coverage ID, handled source IDs and a short account of intent/uncertainties/next step.
Field-complete validators for these three types belong with the implementing tasks.
